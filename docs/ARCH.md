# Arquitetura

Adaptada de [niloodev/vee](https://github.com/niloodev/vee) (`docs/ARCH.md`): MVC + Atomic Design, independente de stack. O vee não tem backend de rede; aqui o mesmo MVC vive em `apps/api`, e a web consome a API.

## Camadas e regra de dependência

Dependências apontam sempre para baixo. Nunca importe de uma camada acima.

**Web (`apps/web/src`)**

```
app/                 ENTRY: rotas Next finas (page.tsx só renderiza a page do módulo)
modules/<feature>/   FEATURE: fatia vertical (components, hooks, services, store, providers)
core/                INFRA da UI: services (http, socket), providers globais, estilos/tokens
shared/              FOLHA: componentes atômicos reutilizáveis e tipos genéricos (não importa modules)
```

- `core/providers/providers.tsx` é o único arquivo de `core` que pode importar `modules`.
- Um módulo pode importar outro módulo apenas pelos barrels públicos (ex.: `@/modules/shell/store`).

**API (`apps/api/src`)**

```
routes/<recurso>/    ENTRY HTTP: chama o controller e traduz o envelope em status (mapa ERROR_STATUS em *.constants)
cli/<comando>/       ENTRY de linha de comando (importRoll20, importRoll20Pages, mediaAssets, setPassword, storage): lê argumentos e chama controllers (storage fala direto com o service de mídia: dump, restore, migrate-local)
realtime/            ENTRY Socket.IO: auth do handshake, handlers por domínio em handlers/<dominio>/
core/controllers/    borda do domínio: valida (Zod do shared), chama models por interface, devolve envelope (exceção: mediaAsset é um orquestrador interno de model + service de mídia, sem envelope, usado pelos outros controllers e pela CLI via `@/core/controllers/mediaAsset`)
core/models/         acesso a dados (Prisma) + mapeamento linha ↔ DTO (*.utils.ts)
core/services/       infra: database (Prisma), auth (argon2/JWT), env (Zod), media (storage S3 local, SeaweedFS: mediaStorage + characterImages + arenaImages + assetFiles com optimizeMap e makeThumbnail, servido em /media), roll20 (conversão pura do export), dice (`serverRandomInt`, o dado do servidor das rolagens e da iniciativa)
middlewares/         requireAuth (sessão + papel lidos do banco), rateLimit (login e API), errorHandler
```

Fluxo: `route → controller → model → services/database`. Routes e handlers nunca tocam Prisma.

**Shared (`packages/shared/src`)**: `schemas/<entidade>/` (Zod é a fonte da verdade; tipos via `z.infer`) e `contracts/` (envelope `ControllerResult`, eventos de socket tipados). Regras puras do jogo entram aqui (ex.: modificador, proficiência) para rodar igual no front e no back.

## Envelope e erros

```ts
type ControllerResult<T, E extends string> = { message: string; payload: T } | { error: E };
```

- Cada controller tem `<x>.errors.ts` com o catálogo (mensagens em PT, exibíveis ao usuário) e `type XError`.
- Teste de falha: `isErrorResult(result)` (de `@magista/shared`).
- A API responde sempre nesse formato; a web (`apiRequest`) devolve o mesmo envelope.
- Services de feature na web: os de ação (login, rolagem) retornam `{ ok: true } | { ok: false; error }` e atualizam o store; os de dados (`fetchCharacter`, `saveSheet`, `levelUp`...) devolvem o envelope `ControllerResult` e quem atualiza o store é o hook da página.
- Salvamento da ficha: autosave com debounce, um salvamento por vez (`flush`), sempre enviando o `updatedAt` de base. Se o servidor tem versão mais nova (Mestre editou ou subiu o nível), o cliente aplica os campos do Mestre (`mergeGmOnlyFields`) sobre o rascunho local e tenta de novo uma vez. Atualizações remotas com edição pendente fazem o mesmo merge em vez de serem descartadas; na aba do Mestre o rascunho dele é mantido inteiro (só a versão de base é atualizada). Se o conflito se repetir, o salvamento falha com "tentar de novo" em vez de ficar preso. A reconciliação é `saveWithReconcile` (`SheetPage.utils.ts`).

## Anatomia de unidade (componente, hook, service, slice, model, controller)

Toda unidade é uma pasta e só é acessada pelo seu `index.ts`.

| Arquivo          | Papel                                                                                                                   |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `X.tsx`          | View: só marcação; desestrutura o retorno do hook. `export function X`, nunca default (exceto arquivos de rota do Next) |
| `X.hook.ts`      | Lógica: um `useX()` que retorna dados, flags e handlers                                                                 |
| `X.types.ts`     | `XProps`, `XHookProps`, tipos locais                                                                                    |
| `X.constants.ts` | Valores fixos: mapas de classes por variante, textos, tempos, polígonos                                                 |
| `X.utils.ts`     | Funções puras auxiliares                                                                                                |
| `X.context.tsx`  | Context + provider + accessor com guarda (stores)                                                                       |
| `X.test.ts`      | Testes (Vitest) ao lado da unidade                                                                                      |
| `subcomponents/` | Filhos usados só por este pai, mesma anatomia, com barrel próprio                                                       |
| `index.ts`       | API pública: `export * from "./X"; export type ...`                                                                     |

Nomes: componentes/pages/providers em `PascalCase/`; hooks, services e slices em `camelCase/`; arquivos de domínio em minúsculo (`account.ts`, `account.types.ts`). Interfaces de domínio com prefixo `I` (`IAccount`, `IAccountModels`, `IAuthController`), constantes em `UPPER_SNAKE`, catálogos `xErrors`, slices `createXSlice` e `defaultXState`.

## Atomic Design (web)

- `atoms`: burros, guiados por props (Button, Input, Icon, Text, Divider).
- `molecules`: composições pequenas, podem ter hook (FormField, PasswordField, Panel).
- `organisms`: regiões inteiras de tela (LoginPanel, LoginBackground, PresencePanel, SessionGate).
- `pages`: compõem organisms, providers e estado; chamadas pelo `app/`.
- UI genérica vai em `shared/components/<nível>`; UI de uma feature em `modules/<f>/components/<nível>`. Cada nível usado tem barrel (não é preciso criar níveis vazios).
- O Figma (página 🧩 Componentes) já está organizado nesses níveis; ver `docs/DESIGN.md` para o mapa nó → componente.

## Estado (web)

Tags especiais: módulo `modules/features` é o registro (`FEATURE_SHEET_SLOTS`) da UI de cada tag na ficha (`FeatureSlots` por slot e `FeatureBadges`); a `SheetPage` só monta os slots. A tag Marcado vive em `modules/marked` (`markedSlice`, services de socket `markedRequests`, `MarkedProvider` no layout `(table)` que escuta os eventos `marked:*` e monta o `MarkedProposalModal` global, `MarkedSoulPanel`, `MarkedSharedTrait`, `MarkedBackdrop`). No servidor, `core/controllers/marked` guarda o chamado pendente em memória e o traço ativo em `marked_shares`; é montado em `realtime.ts` com a presença (`isCharacterAttended`) e os handlers ficam em `realtime/handlers/marked`.

Imagens: o Mestre envia **avatar** (rosto, retratos e futuro token da Arena) e **arte** (corpo inteiro) pelo `NameDialog` de criar ficha e pelo organism `CharacterImagesDialog` (`modules/library`, aberto pelo menu da ficha na biblioteca e pelo botão "Imagens" do cabeçalho da ficha). Toda imagem enviada (avatar, arte, mapa de cena, imagem de NPC, importadores) vira um **asset** compartilhado (`core/controllers/mediaAsset`, `imageAssets.ingest`): o hash sha256 dos bytes identifica a imagem (tabela `media_assets`, model `mediaAsset`), então o mesmo arquivo enviado de novo reaproveita o asset sem duplicar; uma imagem nova é regravada em WebP (`optimizeMap`) e ganha uma miniatura WebP de até 256 px (`makeThumbnail`), em `media/<assetId>/full.<ext>` e `media/<assetId>/thumb.webp`. As colunas `avatarKey`, `artKey`, `mapKey` e `imageKey` guardam a chave do asset; a URL da miniatura sai da própria chave (`thumbUrlOf`), sem consulta extra, e os DTOs trazem `avatarThumbUrl`/`artThumbUrl`, `mapThumbUrl` e `imageThumbUrl`. Retratos pequenos usam `characterPortrait` (shared: miniatura do avatar, avatar, miniatura da arte, arte). Trocar, remover ou excluir solta a imagem (`imageAssets.release`): o asset só é apagado quando nenhuma ficha, cena ou token aponta mais para ele. Chaves antigas (`characters/...`, `arena/...`, `legacy/...`) continuam servidas até `npm run media:assets`, que as move para assets e apaga os assets sem uso. Esta tabela é a base da futura biblioteca de imagens. A gravação da chave não mexe no `updatedAt` da ficha (sem conflito no autosave); a mudança chega aos outros pelo evento `character:images`, aplicado por `applyLibraryImages` e `applySheetImages`.

Janelas (popout): `core/services/windows` (`openPopout({ kind, id })`, registro `POPOUT_ROUTES`) abre uma tela numa janela própria do navegador, nomeada por item (abrir de novo foca a mesma janela; com popup bloqueado cai para nova aba). Hoje só a ficha: rota `(table)/janela/ficha/[characterId]` com `SheetPage variant="window"` (sem "Voltar para a mesa" nem o botão de janela; `SheetSkeleton` e `RouteSkeleton` seguem a variante). Botão `PopoutButton` (`modules/shell/components`) na barra de status da ficha e em cada linha da biblioteca. Cada janela tem socket e `CLIENT_ID` próprios, então edições aparecem nas outras pelo `character:updated`. Novos tipos de janela entram em `POPOUT_ROUTES`. Dentro da Arena a ficha também abre em janelas flutuantes (ver "Fichas na Arena" abaixo).

Perfil: módulo `modules/profile` (organism `ProfileDialog`, aberto pelo botão "Perfil" do cabeçalho da `/mesa`: conta, troca de senha com o service `changePassword` e modo performance). Modo performance: preferência por aparelho no cookie `magista-perf` (`core/services/performance`, `writePerfMode`), lida no `app/layout.tsx` para pôr `data-perf` no `<html>` já no HTML do servidor; o CSS do modo leve está em `core/assets/styles/performance.css` (variante Tailwind `lite:`) e a lógica JS usa `usePrefersReducedMotion`/`prefersReducedMotion` (`shared/hooks`), que somam o modo escolhido ao `prefers-reduced-motion` do sistema.

Biblioteca de fichas: módulo `modules/library` (organism `CharacterLibrary` na `/mesa`, `FolderTree` com dnd-kit para o Mestre, lista plana para o jogador e para a busca; `librarySlice` com dados, busca e pastas expandidas, salvas por visitante no `localStorage`). Movimentos são otimistas (`applyMove`, mesma regra do servidor) e desfeitos se a API recusar. Ficha: o `sheetSlice` guarda as fichas abertas na aba por id (`sheets[characterId]`, cada uma com carregamento, rascunho e autosave próprios; respostas de uma ficha que não foi aberta são ignoradas), e a `SheetPage` lê só a entrada do seu id, então trocar de ficha vai direto ao skeleton. Posição e pasta das fichas são gravadas por SQL direto, sem mexer no `updatedAt` usado na concorrência do autosave. Listas da ficha usam o organism genérico `shared/components/organisms/SortableList`.

Arena: estudo e plano em `docs/ARENA.md`. No servidor, `core/controllers/arena` (cenas, cena ativa no singleton `arena_state`, tokens de ficha e de NPC, movimento) com models `arenaScene` e `arenaToken`; o controller devolve a audiência (`table` ou `gm`) e as rotas e `realtime/handlers/arena` chamam os broadcasters de `realtime.ts`. Regras puras em `packages/shared/src/game/arena` (`canControlToken`, `clampToMap`) e contratos em `schemas/arena`. Renomear, trocar imagens, mudar acesso ou excluir uma ficha manda `arena:scene` com `sceneId: null` (`broadcastArenaRefresh`). Tabuleiro: cada cena tem um tamanho em px do mundo (`boardWidth`/`boardHeight`, o Mestre escolhe em unidades de 70 px pelo `SceneBoardDialog`) e o tamanho natural do mapa (`mapWidth`/`mapHeight`, lido no upload); as regras `fitBoard`, `resolveBoard` e `scaleBoardPoint` (shared) mantêm sempre a proporção do mapa, e o DTO traz `width`/`height` resolvidos. Mudar o tabuleiro ou trocar o mapa reescala as posições dos tokens na mesma transação; o renderer estica o mapa no tabuleiro e compensa o zoom. Cenas gravadas antes disso são medidas uma vez, lendo o mapa do storage, no primeiro `GET /arena` ou `GET /arena/library`. Os mapas enviados são regravados em WebP (`optimizeMap` em `core/services/media`). Cenas ficam numa biblioteca com pastas (`arena_scene_folders`, model `arenaSceneFolder`, mesma regra de ordem da biblioteca de fichas). A árvore com pastas e arrastar e soltar é o organism genérico `FolderTree` (`modules/library`), parametrizado pelo tipo de folha (ficha ou cena), com os utilitários `applyTreeMove`, `moveForTreeDrop` e `countLeavesDeep` em `library.utils`; a biblioteca de fichas e a de cenas (`SceneLibrary`) usam o mesmo componente. Rolagens: o servidor anuncia cada rolagem na hora com `roll:pending` (quem rola o quê e quando revela, sem os dados) e o resultado chega depois em `roll:result`; o `tableSlice` guarda as pendentes e só o feed da Arena as mostra. Na web, rota `(table)/arena` com a `ArenaPage` de `modules/arena`: `arenaSlice` (visão carregada, seleção e janelas e abas encaixadas), services `arenaRequests` (`fetchArena`, `moveArenaToken` com ack, sem prévia de arraste) e o renderer PixiJS em `services/arenaRenderer` (classe imperativa: mapa, câmera, tokens, arraste; desenha só quando algo muda), carregado por `import()` dinâmico no organism `ArenaStage`, então o `pixi.js` só entra no bundle da Arena (fora dele, só `import type`). Criação de tokens pelo Mestre no hook `modules/arena/hooks/useArenaTokenPlacement` (services `createArenaToken` e `uploadArenaTokenImage`): a `CharacterLibrary` recebe `onPlaceCharacter` (item "Colocar no mapa") e `onDropCharacter` (o `FolderTree` com `freeAxis` chama `onDropOutside` com o ponto da página ao soltar fora da árvore, e o `outsidePreview` troca a prévia da linha pelo token enquanto o ponteiro está sobre o mapa; a Arena passa `isOverMap` e o tamanho pelo `zoom` do renderer), e o renderer converte o ponto com `clientToWorld` (nulo sob os painéis) ou usa `visibleCenter`, expostos no `controlsRef` do `ArenaStage`. O hook da página ouve `arena:*` no socket da aba, refaz o fetch em `arena:scene` e ao reconectar, move com otimismo e recarrega a cena se o servidor recusar.

Fichas na Arena: clicar numa ficha da barra lateral, ou "Abrir ficha" no menu do token (botão direito ou Shift+F10), abre a ficha numa janela flutuante (`ArenaSheetWindows` com o organism genérico `shared/components/organisms/FloatingWindow`: arrastar pela barra de título, redimensionar pelo canto, Alt e as setas pelo teclado; posição e tamanho salvos por ficha no `localStorage`). As janelas abertas ficam no `arenaSlice` (`openSheets` é a pilha, a última na frente, até `ARENA_SHEET_WINDOWS_MAX`; `sheetSlots` dá a cada uma um lugar fixo de renderização e de cascata, para trazer à frente sem mover o DOM). Soltar a janela sobre o painel de rolagens ou sobre a barra lateral (ou usar os botões de encaixe da barra de título) a encaixa como aba daquele painel (`docked` e `dockTab` no `arenaSlice`, `ArenaDockedSheet` com "Soltar em janela" e "Fechar ficha"). A ficha usa `SheetPage variant="panel"`: sem link de pular conteúdo, sem coluna nem aba de rolagens, nome em `h2`, abas `dense`, e a animação de dados num portal no `body`. Os cortes da ficha são container queries (`@min-[37rem]` a `@min-[93rem]`, os cortes de tela menos o respiro de 2rem da página e uma folga para a barra de rolagem clássica) num contêiner logo abaixo da raiz, então a ficha se adapta à largura da janela ou do painel e na página fica igual a antes. Os painéis laterais encolhem juntos (`fitPanels`, sem passar do mínimo) para sempre sobrar `ARENA_MAP_MIN_WIDTH` de mapa.

Status dos tokens (vida e sanidade): o token de ficha lê `sheet.resources` e o NPC as colunas próprias (`healthCurrent`... em `arena_tokens`); quem vê é decidido por `canSeeTokenStatus` (shared): o Mestre, as contas com acesso à ficha, as contas em `arena_token_status_viewers` ou todos com `statusPublic`. O status não entra no `IArenaToken` (que é igual para a sala toda): o `GET /arena` traz `statuses` filtrado por quem pede (e `statusAccess` só para o Mestre), e o model `arenaToken.listStatuses` lê só `sheet -> 'resources'` numa consulta. Mudanças vão por `arena:status` (o Mestre recebe com as permissões; cada token visível vai só às salas autorizadas, `character:<id>`, `account:<id>` ou `table:main` se público, e quem perdeu a permissão recebe `status: null`), montado por `statusEmits` em `realtime.utils`. Ficha salva: o `broadcastCharacterUpdate` chama `broadcastCharacterStatus`, que só quando os recursos mudam manda `arena:character-status` às contas que veem a ficha apenas pelo token. "Aplicar mudança" (`arena:apply`, qualquer conta, em tokens que ela vê; limite próprio igual ao das rolagens): `arena.applyChange` aplica `applyResourceChange` (shared) com trava de linha (NPC nas colunas, ficha por `jsonb_set` em `characters.changeResource`, uma vez por ficha, movendo o `updatedAt`), e o handler manda `arena:effect` (só a quantidade e o `attackerTokenId` quando quem recebe vê o atacante, para a animação; o atacante opcional precisa estar visível, na mesma cena e ser controlado por quem aplica), `arena:status` dos NPCs e `character:updated` das fichas. Na web, `useArenaTokenStatus` (`modules/arena/hooks`) ouve esses eventos, abre o menu `ArenaChangeMenu` e o modal `ArenaTokenSettingsDialog`; o renderer desenha as barras (`services/arenaStatusBars`) e as animações (`services/arenaTokenEffects`), os dois só carregados com o Pixi. A ficha aberta com edição pendente aceita o `resources.*.current` do servidor quando o rascunho não mexeu nele (`mergeRemoteResources`, base em `baseResources` do `sheetSlice`).

Mapa Mundi: um modo especial da Arena, não uma cena. No servidor, o singleton `arena_state` guarda `worldMapLive`, a posição do token do grupo (`partyX`, `partyY`) e a névoa (`fogMask`, um bitset da grade de `WORLD_FOG_CELL` px, e `fogVersion`); model `arenaWorld` (a névoa muda numa transação com `FOR UPDATE`) e controller `core/controllers/arenaWorld` (`setLive` e `paintFog` só do Mestre, `moveParty` do Mestre sempre e do jogador só com o mundo no ar). `arenaScene.findActiveSceneId` devolve a cena **efetiva** (null com o mundo no ar), então todas as regras de token, audiência e turnos tratam a cena guardada como fora do ar sem mudar; o `findLiveState` traz a cena guardada e o `worldMapLive` para o `getView` e para "Voltar à cena". Regras puras em `packages/shared/src/game/worldMap` (`paintFog`, `fillFog`, `encodeFogMask`, `canMoveParty`, `clampToWorld`) e schemas em `schemas/arena/arena.world.ts`. O `GET /arena` traz `worldLive` e, quando mostra o mundo, `world` (`party`, `fog` em base64, `fogVersion`) com `scene`, `tokens` e `turnOrder` vazios. Socket: `arena:world-move` e `arena:world-paint` (cliente, com ack; o pincel tem gate próprio de 24/s) e `arena:world-party` e `arena:world-fog` (servidor, para a mesa com o mundo no ar, senão só para o Mestre; a névoa vai inteira, então um evento perdido se corrige no próximo). Na web, `useArenaWorld` (`modules/arena/hooks`) ouve os eventos, move o grupo com otimismo, põe o mundo no ar e dá ao Mestre o pincel: os segmentos viram lotes enviados a cada `WORLD_PAINT_FLUSH_MS`, e os lotes sem confirmação ficam pintados sobre a névoa do servidor (`shownFog`; a confirmação de um lote envia antes o que está sendo juntado, então o traço nunca pisca); enquanto a aba move o grupo, os ecos dos próprios movimentos são ignorados e só a resposta mais nova vale. A imagem é fixa (`apps/web/public/arena/world-map.jpg`, 4096 px) e a rota da Arena a pede com `preload` de alta prioridade como `fetch` (`services/arenaPreload`). Versão do app: `core/services/version` (`APP_VERSION`, do `package.json` da web pelo `next.config`, e `versionedUrl`): os assets do app e todas as mídias (`toMediaUrl`) levam `?v=<versão>`, então ficam em cache para sempre e são baixados de novo quando a versão sobe (`npm run version:bump`); o aparelho lembra a última versão carregada (`magista-app-version`) e a tela de carregamento diz que está atualizando. Assets estáticos em geral passam pelo `core/services/assets` (`loadAsset` baixa uma vez por aba com progresso e guarda o blob; `warmAsset` só põe uma mídia no cache do navegador, sem guardar os bytes; `preloadAssets` soma o progresso de uma lista): a Arena lista os dela em `ARENA_ASSETS`, o hook `useArenaAssets` os carrega ao abrir, junto com o mapa de todas as cenas (`GET /arena/maps`, o da cena no ar primeiro, só no cache; `ARENA_ASSET_CONCURRENCY` downloads por vez, a tela espera no máximo `ARENA_ASSET_FILES_LIMIT_MS` e o resto segue em segundo plano; com economia de dados ligada, só os arquivos da Arena) e o aquecimento das animações (`warmEffects` do renderer: toca cada efeito uma vez, no alvo e no atacante, fora de vista e sem desenhar mapa nem tokens, para compilar os shaders; um efeito real que chegue nesse meio tempo espera o aquecimento limpar o que criou), e mostra a tela `AssetLoadingScreen` (`shared/components/organisms`, também no `RouteSkeleton` da Arena, então é a primeira coisa na tela) por no mínimo `ARENA_ASSET_SCREEN_MIN_MS`, e o renderer decodifica o mapa do mesmo blob, sem baixar de novo. No renderer, a cena tem `kind` (`scene` ou `world`): o grupo é um pseudo-token (`WORLD_PARTY_ID`, `party: true`) desenhado pelo `ArenaPartyToken` (`services/arenaPartyToken`, a runa Othala em energia trocando entre `WORLD_PARTY_COLORS`), as nuvens são o `ArenaWorldClouds` (`services/arenaWorldClouds`, um mar de nuvens procedural num shader, sem fluido) e a troca entre cena e mundo toca o `ArenaWorldTransition` (`services/arenaWorldTransition`) com uma interpolação de câmera (`tweenCamera`); o voo toca só para os jogadores (`setPassages`, o Mestre troca na hora; a câmera não é salva enquanto o mapa carrega ou a câmera voa, e o tabuleiro antigo não é desenhado sob as nuvens opacas) e uma troca no meio do voo nunca o cancela (`regather`: as nuvens voltam a engrossar de onde estão e o pouso vai para o mapa mais novo); o renderer prepara o mundo ocioso (`warmUp`: compila os shaders das nuvens, do voo e do token e sobe a textura com mipmaps, guardada enquanto o renderer vive); detalhes do visual em `docs/VFX.md`. O Mestre abre o mundo em prévia pela linha `WorldMapRow` fixa no topo da aba Mapas (`viewSceneId = ARENA_WORLD_VIEW`) e pinta pelo `ArenaWorldFogTools`.

Ordem de turnos (o "Turn Order" do Roll20): uma por cena, por token. No banco, `arena_turn_entries` (token único, valor e posição) e, na cena, `turnRound` e `turnTokenId`; model `arenaTurn` (`findOrder` e `change`, que trava a linha da cena e grava a ordem inteira num upsert); controller `core/controllers/arenaTurn` (comandos `arena:turn`: o Mestre faz tudo, o jogador só encerra o turno de um token que controla e rola a iniciativa dos próprios tokens ainda sem valor; "Rolar iniciativa" não muda a ordem na hora: o controller devolve as rolagens (`IArenaTurnRolls`: os NPCs, rolados `1d20 + initiativeBonus` no servidor e guardados em segredo até a revelação, e os tokens de ficha que a mesa vê, que o handler rola pelo `rollController.rollInitiatives` (a ficha lida uma vez, uma rolagem por token, com `tokenId`) como rolagens normais da ficha, no feed; os tokens de ficha ocultos, sem nome ou fora da cena no ar rolam em segredo como os NPCs), com uma trava em memória para o mesmo token não rolar de novo antes de revelar; `recordInitiative` põe na ordem a Iniciativa rolada na ficha na revelação (todos os tokens da ficha na cena ativa) e `recordRolled` grava de uma vez, numa transação e num broadcast, tudo o que um comando do menu rolou). Regras puras no shared (`placeTurnEntries`, `sortTurnEntries`, `moveTurnEntry`, `advanceTurn`, `removeTurnEntries`, `visibleTurnOrder`, `canEndTurn`, `tokenInitiativeExpression`). No `realtime.ts`, `publishToTable` chama `recordInitiative` na revelação de uma rolagem de Iniciativa (os tokens da ficha na cena ativa entram ou mudam de valor), `broadcastRollResult` avisa as linhas que vão girar (`arena:turn-pending`, pelo `initiativePending`), `startTurnRolls` faz o mesmo com as rolagens do menu e revela os NPCs depois de `ROLL_REVEAL_DELAY_MS`, e `broadcastTurnOrder` manda a ordem inteira ao `table:gm` e a cópia sem tokens ocultos ao resto da mesa (só na cena ativa); ocultar, mostrar ou remover tokens manda a ordem de novo (`refreshTurnOrders`), e o `arena.deleteToken(s)` passa a vez antes de remover o token da vez. O `GET /arena` traz `turnOrder` filtrado por quem pede. Na web, `useArenaTurns` (`modules/arena/hooks`) ouve `arena:turns`, manda os comandos (`sendArenaTurnCommand`), guarda a ordem no `arenaSlice` fora do `view` (`turnOrder`, para passar a vez não refazer os tokens; uma ordem igual à atual é ignorada) e as linhas que estão rolando (`turnRolling`, `markTurnRolling`/`expireTurnRolling`), anuncia a vez em `aria-live` e dá ao menu do token "Rolar iniciativa", "Adicionar à iniciativa" e "Remover da iniciativa"; a janela é o organism `ArenaTurnWindow` (sobre o `FloatingWindow`), e o renderer marca o token da vez com `setTurnToken` (`services/arenaTurnAura`: o token flutua um pouco sobre um anel de energia rubi que solta fios para fora; com só a aura em movimento o loop roda a ~30 fps, e no modo leve fica parado).

Tokens dos jogadores: o jogador cria tokens das próprias fichas na cena ativa. A lista plana dele (`CharacterRowList`) arrasta pelo drag nativo com a ficha em `CHARACTER_DRAG_TYPE` (`useCharacterRowDrag` esconde o fantasma do navegador e desenha a mesma prévia do Mestre, movendo o nó por ref), o `useArenaFileDrop` do `ArenaStage` entrega o id ao `useArenaTokenPlacement`, e o menu da linha tem só "Colocar no mapa". O `GET /arena` do jogador traz em `controllableCharacterIds` todas as fichas liberadas para a conta, então um token novo delas já se move; remover passa por `authorizeMany`.

Token isométrico: o DTO do token traz `style` (`portrait` ou `figure`), o estilo **efetivo** calculado em `tokenImageUrls` (`core/models/arenaToken`): o NPC usa a própria imagem e a coluna `tokenStyle` (sem imagem é sempre `portrait`); o token de ficha usa `figureKey` quando a ficha escolheu `figure` (coluna `characters.tokenStyle`) e tem a imagem, senão o avatar ou a arte. O renderer desenha o `figure` sem máscara nem anel, com o maior lado igual a `size` e a proporção da textura (`tokenExtents`), sobre uma elipse no chão no tom do token; o servidor não conhece a proporção. Menu do botão direito (`ArenaTokenMenu` e o hook `useArenaTokenActions`): age sobre a seleção (o token clicado fora dela é selecionado antes) e guarda a cópia do Ctrl+C no `arenaSlice` (`tokenClipboard`, por aba, sobrevive à troca de cena e ao `resetArena`); colar usa `pastePlacements` (o grupo centrado no ponteiro, ou uma unidade ao lado). Imagens soltas do computador no mapa: `useArenaFileDrop` no `ArenaStage` e `dropImages`/`submitImageDrop` no `useArenaTokenPlacement`, com o `ArenaImageTokenDialog` sugerindo o estilo pela transparência da borda (`hasTransparentEdges`).

Efeitos de dano e cura: **adicionar um efeito** = um id em `ARENA_EFFECT_STYLES` (shared, validado no `arena:apply`), uma entrada em `ARENA_EFFECT_CATALOG` (`modules/arena/arena.constants`: nome, descrição, tags `damage`/`heal`/`health`/`sanity` que alimentam os filtros do seletor, cor e se o atacante voa ou conjura) e o registro em `ARENA_EFFECT_PLAYERS` (`services/arenaEffectPlayers`: a classe do alvo e a do atacante); os tipos `Record<ArenaEffectStyle, ...>` recusam um efeito faltando. O mapa (`arenaRenderer`) e o exemplo do seletor (`arenaEffectPreview`) usam a mesma fábrica, então o efeito novo já aparece nos dois. A tag `free` marca os efeitos livres (sem ação padrão, filtro "Livres"); o atacante pode ser `lunge`, `cast` ou `shot`, e o registro pode devolver `leadMs` (a animação do alvo começa antes do golpe, para sincronizar um preparo; o status muda no `hitMs`). Armas corpo a corpo (a pá da Pazada, o machado do Ataque Vodu) ficam na mão de quem ataca: `ArenaWeaponLungeEffect` compõe o `ArenaLungeEffect` (rastro sob o token) com a arma desenhada sobre ele, erguida no avanço e baixada na chegada, e o alvo só toca o impacto. Efeitos que envolvem a tela (Vox Populi) usam a camada `ArenaFxScreen` do host (`screen`: camada em coordenadas de tela, `toScreen`, `addWorldFilter`/`removeWorldFilter` para filtros sobre o mundo e `claim` para tocar a parte de tela uma vez só num dano em área, `reserve` para limitar quantas peças caras de um tipo tocam ao mesmo tempo, como o fluido de fogo por alvo do Vodu, e `field`, a área do efeito: a tela inteira e uma margem além das bordas (`ARENA_FX_FIELD_MARGIN`), para nenhuma borda aparecer; os tamanhos das partículas e as distâncias seguem o raio do token na tela). A parte de tela de cada Ultimate é desenhada em volta do alvo, num grupo que segue a posição dele na tela e o zoom a cada quadro, então nada fica para trás quando a câmera se mexe; escuridões e clarões são suaves (`paintFalloff`, `paintGlow`), sem bordas retas. Num dano em área o renderer passa a cada efeito o `group` (onde estão todos os alvos, em raios do token) e as Ultimates mostram uma peça central só sobre o grupo (uma vidraça, um buraco negro, uma Flor da Vida, a lua, o selo e a pá), maior conforme o grupo se espalha, com as correntes e as sombras divididas entre os alvos. Fluxo de energia (`services/arenaEnergyFlow`, genérico para qualquer efeito): `ArenaEnergyFlow` é uma malha ao longo de qualquer caminho, aberto ou fechado (`circlePath`), com um shader de fluido procedural (ruído distorcido duas vezes por ele mesmo, esticado ao longo da faixa, com veios de luz nas curvas de nível e o miolo branco onde a energia é mais densa); recebe paleta (`ENERGY_PALETTES`: `gold`, `holy`, `hextech`), velocidade, comprimento de onda, nitidez e quantidade de fios, e mostra de `tail` a `head` (a energia entra e se esgota); a geometria só é refeita em `setPath`, o resto é uniforme do shader. Com `blend: "normal"`, a paleta `shade` e `density` alta, a mesma fita desenha um corpo escuro de borda macia em vez de luz (o corpo das sombras de Nox). `ArenaEnergyChannel` (no `arenaEnergyFlow`) é um canal de energia entre dois pontos: uma faixa longa de `ArenaEnergyFlow` numa curva suave (`channelPath`) que balança devagar, estendida por `head` e esgotada por `tail`; é o jeito de levar energia de um lugar a outro com rumo (a crença do Vox, a descida do Chamado Divino). Fluido de energia em GPU (`services/arenaEnergyFluid`, genérico, a melhor qualidade do kit; o guia de uso e as receitas de visual estão em `docs/VFX.md`): `ArenaEnergyFluid` é uma simulação Stable Fluids em texturas `rgba16float` (velocidade e pressão em 192 células, tinta colorida em 640 texels): a cada quadro o que o efeito põe em `sources` é despejado como tinta, na proporção do tempo do quadro; a velocidade recebe a turbulência (_curl noise_), o viés do efeito (deriva, despejar de ou para um ponto, girar em volta dele) e o confinamento de vorticidade, a pressão é resolvida por Jacobi, e velocidade e tinta são advectadas e dissipadas. No modo `water` a tinta é a profundidade de um corpo de água, sombreada como superfície molhada (reflexos nítidos, cáusticas, espuma nas bordas, translúcida no raso): a água do Antropozohl. No modo `fire` a tinta é calor: queima de branco no miolo pela paleta (`core`, `mid`, `deep`) até as pontas, rasgada em línguas que sobem, e com `secondary` as fontes vermelhas queimam numa segunda paleta, misturando dois fogos (o fogo do Vodu, no alvo, no machado e na bola de fogo). Todos os modos somem suavemente perto da borda da área, então o fluido nunca aparece cortado em retângulo. No modo `shadow` (`mode: "shadow"`), a mesma névoa vira uma sombra viva: escura, cobrindo a cena (mistura normal), com as bordas rasgadas acesas na cor da tinta e os veios brilhando por dentro (a Reencarnação da Morte e o atacante dela). `view` não mostra a tinta em si (isso parece tinta): mostra uma névoa translúcida na cor da tinta, rasgada em fiapos por um ruído que a própria tinta entorta, com veios de luz suaves, e nunca estoura em branco. `ArenaEnergyTendril` é o jeito de levar energia de um ponto a outro: alguns fios finos e nítidos trançados na mesma curva (`view`, que vai para a cena) e uma faixa invisível mais larga que despeja a tinta no fluido, então o fio deixa um rastro de névoa que se enrola e some. Com `inject: 0` o fluido segue escorrendo e se apaga sozinho: as Ultimates com fluido (Vox Populi, Chamado Divino) seguram o efeito por `FLUID_LINGER_MS` depois do fim (`linger`) numa camada própria, fora do esmaecimento da parte de tela. As renderizações fora da tela passam por `IArenaFxScreen.renderTo`. Enxames (`services/arenaButterflySwarm`, genérico): `ArenaButterflySwarm` voa borboletas planejadas de uma vez, cada uma com um caminho em função do tempo, batendo as asas e virando a cabeça para onde vai, em dois lotes (silhuetas e brilhantes). Som visível (`services/arenaSoundWave`, genérico): `ArenaSoundWaveFilter` é um filtro sobre o mundo em que cada onda é uma faixa de ar comprimido saindo de um ponto (até 8 ao mesmo tempo, cada uma com raio, força, espessura e abertura da frente em volta de uma direção); dentro da faixa a imagem é empurrada para fora e puxada de volta, então mapa e tokens ondulam quando a onda passa, com as cores se separando um pouco na crista (a voz da Marion no Vox Populi). Vidro quebrado (`services/arenaGlassShatter`, genérico): `ArenaGlassShatterFilter` é um filtro sobre o mundo (`addWorldFilter`) que quebra a imagem como uma vidraça atingida num ponto: cacos em células de Voronoi num espaço log-polar (longos, radiais e menores perto do impacto), cada um deslocando a imagem atrás dele e refletindo a luz no próprio ângulo, rachaduras finas de luz que correm para fora até `reach`, o centro estilhaçado, e frestas que se abrem com `breakup`; tudo em pixels de tela, atualizado por quadro com `update`. Quando uma animação termina, o que sobrou dela se dissipa em `EFFECT_LINGER_MS` em vez de sumir (`fadeEnded` no renderer), e a parte de tela das Ultimates se dissolve a partir de `ARENA_FX_FADE_FROM`; os canais têm bordas que se rasgam em fiapos (`feather`). Cada efeito pode declarar `impactMs`, o instante do golpe na animação; as barras de vida e sanidade só mudam nesse instante (`holdStatusUntil`); Animações preferidas da ficha: `sheet.effects` (`sheetEffectsSchema`, ação × atributo → estilo, default `{}`) é salva pelo autosave normal (não é campo do Mestre) e vem no resumo da biblioteca; com o efeito em Automático e um atacante de ficha, `arena.applyChange` lê a ficha do atacante e resolve `resolveAutoEffect` (shared), mandando o efeito explícito no `arena:effect`. Na web o rótulo "Automático (X)" do `ArenaChangeMenu` usa a mesma regra com o resumo da biblioteca (`applyLibraryEffects` ao salvar), e o modal `SheetEffectsDialog` (`SheetHeader`) reaproveita o `ArenaEffectPickerDialog` carregado sob demanda (exceção aceita à direção sheet → arena: o módulo `sheet` lê o `ARENA_EFFECT_CATALOG` e abre o seletor da Arena; se o catálogo crescer para outros usos, ele sai para um módulo neutro).

Na web existe um único socket por aba, criado por `modules/table/providers/TableSocketProvider` (layout `(table)`) e lido com `useTableSocket()`.

Zustand 5 com slices: cada feature tem `store/<x>Slice/` (`XState`, `XActions`, `defaultXState`, `createXSlice`). `modules/shell/store/appSlice` combina todos em `createAppStore()` e expõe `useApp(selector)` via context (store criado uma vez por montagem, nada de singleton global). Dados assíncronos ficam como `{ status: LoadStatus, data }`.

## Tempo real

- Socket.IO autenticado pelo mesmo cookie de sessão (`realtime/realtime.auth.ts`).
- Eventos tipados em `packages/shared/src/contracts/socket.events.ts` (`ServerToClientEvents`, `ClientToServerEvents`, `SocketData`). Todo evento novo nasce ali.
- Salas: `table:main` (mesa), `table:gm` (Mestre), `character:<id>` (sockets de todas as contas com acesso à ficha; entram ao conectar e são sincronizados por `syncCharacterAccess` quando o acesso muda ou a ficha é excluída) e `account:<id>` (para derrubar sockets no logout e avisar a conta).
- Handshake só aceito da origem `WEB_ORIGIN`; cada socket tem limite de rolagens (6 a cada 5s).
- Eventos atuais: `presence:update`, `roll:history` (últimas 50 rolagens, em memória, enviadas ao conectar), `character:updated` (ficha salva, com `origin` = id da aba que salvou, enviado no header `x-magista-client`), `presence:ping` (cliente, só ack, a cada `LATENCY_PING_INTERVAL_MS`; o servidor responde no máximo um por segundo por socket e o cliente guarda a latência no `tableSlice`), `roll:request` (cliente pede com ack), `roll:pending` (para a mesa toda assim que alguém rola: quem, o quê e quando revela, sem os dados; a Arena mostra o cartão em suspense até o `roll:result`), `sheet:ping` (cliente mostra um traço ou item da ficha à mesa, com ack; mesmo limite das rolagens, entra no histórico e sai na hora, sem animação), `roll:result` (para a mesa toda) e `library:changed` (sem payload; a biblioteca mudou, o cliente refaz o fetch: vai para `table:gm` e para as contas afetadas) e `character:images` (`{ id, avatarUrl, artUrl, figureUrl, tokenStyle, showTokenName }` e as miniaturas para `table:gm` e `character:<id>` quando o Mestre troca uma imagem), `character:features` (`{ id, features }`, mesmo destino, quando o Mestre muda as tags) os da Arena: `arena:move` (cliente, com ack, grava; os outros só recebem a posição final e o token desliza até ela, sem prévia ao vivo durante o arraste), em lote `{ moves }` (até 50 tokens; a autorização é feita de uma vez por mensagem e o ack traz os tokens gravados e os recusados), `arena:token`, `arena:token-removed`, `arena:tokens` e `arena:tokens-removed` (os dois em lote: um evento por sala quando um movimento em grupo, uma edição ou uma remoção atinge vários tokens) e `arena:scene` (servidor; `{ sceneId }`, o cliente refaz o `GET /arena`, `null` = qualquer cena); token visível da cena ativa vai para `table:main` e o resto só para `table:gm` (ocultar manda `arena:token-removed` (ou `arena:tokens-removed` em lote) aos jogadores com `except(table:gm)`); os de status e dano: `arena:status`, `arena:character-status`, `arena:effect` (servidor) e `arena:apply` (cliente, com ack); os do Mapa Mundi: `arena:world-move` e `arena:world-paint` (cliente, com ack), `arena:world-party` e `arena:world-fog` (servidor); os da ordem de turnos: `arena:turn` (cliente, com ack que traz a ordem que a conta vê; limite próprio de 12 a cada 5 s), `arena:turns` (servidor, a ordem inteira para `table:gm` e a cópia sem tokens ocultos para os jogadores, só da cena ativa) e `arena:turn-pending` (servidor, `{ sceneId, tokenIds, revealInMs }`: tokens rolando iniciativa, cuja linha gira até a revelação; o tempo é relativo para não depender do relógio do cliente); e os da Marca: `marked:propose`, `marked:answer`, `marked:cancel`, `marked:stop` (cliente, com ack e o mesmo limite das rolagens), `marked:proposal`, `marked:resolved` e `marked:share` (servidor, para `character:<id>` de cada Marcado e `table:gm`; `marked:share` também vai a cada socket ao conectar, se ele vê algum Marcado).
- Rolagens acontecem no servidor a partir da ficha salva (`buildRollSpec` + `rollSpecRows` do shared, que maximiza o dano no crítico); o cliente só diz o que rolar. Pings usam `buildPingSpec` e viram um cartão do feed sem linhas de dados (`kind` `trait` ou `item`). A web salva pendências (`flush`) antes de rolar.
- Quem rola recebe o resultado na hora pelo ack (para tocar a animação `DiceRollOverlay`); a mesa toda (inclusive quem rolou) só recebe `roll:result` depois de `ROLL_REVEAL_DELAY_MS` (fases rolling + adding de `ROLL_PHASES_MS`, no shared), para ninguém ver o resultado antes da animação.
- Handlers em `realtime/handlers/<dominio>/` chamam controllers, nunca models.

## Testes

- **Unitários (Vitest)**: arquivo `X.test.ts` ao lado da unidade em `packages/shared`, `apps/api` e `apps/web` (funções puras, controllers com dependências falsas, slices do store).
- **E2E (Playwright + axe)**: workspace `e2e/`, um spec por fluxo de funcionalidade (`auth`, `sheet`, `sheet-reorder`, `library`, `images`, `window`, `modals`, `rolls`, `ping`, `profile`, `levelup`, `marked`, `arena`, `arena-gm`, `arena-tokens`, `arena-sheets`, `arena-token-status`, `arena-token-figure`, `arena-player-tokens`, `arena-turns`, `arena-world`, `sheet-effects`, `a11y`; o Chromium do e2e roda com WebGL por SwiftShader para a Arena); nada de medir layout ou skeleton no e2e (isso fica com a revisão visual do usuário). O `global-setup` reseta a ficha do personagem de teste do seed via API. Rolagens determinísticas no e2e: interceptar o WebSocket (`routeWebSocket`) em vez de depender da sorte. Specs que abrem uma segunda conta com `browser.newContext()` importam o `test` de `e2e/support/test.ts`, que fecha esses contextos ao fim de cada teste (senão as páginas antigas seguem vivas e pesam no resto da suíte). `holdApi` (`e2e/support/hold.ts`) segura requisições quando um teste precisa de um estado intermediário (e serve para ver skeletons ao conferir o visual).

## Definition of Done

- Pasta por unidade, acesso só pelo `index`.
- View sem estado, efeito ou handler inline com lógica.
- Tipos em `.types`, valores fixos em `.constants`.
- Imports com alias `@/` e por barrel; relativo só dentro da própria pasta.
- Controller valida com schema do shared, chama model pela interface, devolve envelope com erro do catálogo.
- Entry (rota, handler) fino.
- Regra de dependência respeitada.
- Todo carregamento da API com skeleton fiel ao componente (`docs/RULES.md`), validado na revisão visual do usuário.
- `npm run lint`, `npm run typecheck`, `npm test` verdes (e `npm run test:e2e` quando o fluxo de usuário mudou).

## Anti-padrões

Pastas técnicas globais (`utils/` solto, `helpers/`), store singleton global, view ou route acessando persistência, tipos escritos separados da validação, lógica de regra do jogo duplicada entre web e api.
